# 要件定義

## 1. 背景と目的

- X（旧 Twitter）上で、**自分のブラウザにだけ**特定のポストに「クソリプ（インプレゾンビ的なリプライ）」が大量についている**ように見せる** Chrome 拡張を想定する。
- 実際の投稿・他者の表示・サーバー上のデータには**一切影響しない**（ローカル演出のみ）。
- **ポスト詳細画面に限定**して挙動を発火させ、タイムライン全体などへの波及を避ける。

## 2. ステークホルダーと利用シナリオ

- **利用者**: 本人の画面でのみ演出を確認したいユーザー。
- **シナリオ例**: 詳細ページを開くと、元ポストに紐づいた（またはそれっぽい）偽リプが並ぶ。拡張をオフにすると通常表示に戻る。

## 3. 機能要件（要約）

| ID | 要件 |
|----|------|
| R-01 | 対象は **ポスト詳細 URL** のみ（ホーム TL 等では本機能を動作させない）。 |
| R-02 | 偽リプの文言は、(1) **LLM API** で元ポストに関連するインプレゾンビ風に生成する、または (2) **API 未使用・失敗時**は事前定義のプリセットからランダムに選ぶ。 |
| R-03 | 拡張の **ON/OFF** を切り替え可能とする。 |
| R-04 | X 側の UI 更新により偽リプノードが消える場合に備え、**再表示**できること（検討で合意した「次点」アプローチ）。 |
| R-05 | （任意・拡張フェーズ）X の**一部更新通信**を抑止し、偽リプ表示との競合を減らす余地を残す。 |

## 4. 非機能要件

| ID | 要件 |
|----|------|
| N-01 | API キー等の秘密情報は **拡張内ストレージ**に保存し、リポジトリや平文ログに含めない。 |
| N-02 | LLM 出力を DOM に反映する際、**XSS を避ける**（例: `textContent` によるテキストノード挿入を原則とする）。 |
| N-03 | X の DOM/CSS 変更に強いわけではないため、**保守可能な範囲**でセレクタや挿入位置を局所化する。あわせて、偽リプ行は **公式ポスト行の構造・見た目に寄せた DOM/CSS**（自前接頭辞・安定 `data-testid` は読み取りのみ）とし、ハッシュ付き公式クラスには依存しない。 |
| N-04 | 過度な API 呼び出しを避けるため、**同一ポスト詳細 URL に対する生成結果のキャッシュ**等を検討する。 |

## 5. 制約・前提

- 対象オリジンは **https://x.com/** および必要に応じて **https://twitter.com/**（同一機能の URL 互換）。
- Chrome **Manifest V3** を前提とする。
- LLM 呼び出しは利用者が用意した **エンドポイント/API キー**（例: OpenAI 互換）を想定する。拡張が独自に課金するわけではない。

## 6. スコープ外（本ドキュメント時点）

- 他ユーザーの画面への影響、サーバー改ざん、公式 API の不正利用。
- **X の管轄外に完全独立したオーバーレイ常設**を第一手段とする設計（検討では最も安定だが、当面は「次点」に留める。必要になれば将来オプション化）。
- 「見た目だけ（CSS のみ）で公式 DOM の数値・新着を完全固定」することを**主手段**とする（現実的でないため）。

## 7. 合意した設計方針（検討の要約）

- **優先する現実解（「次点」）**: 公式リプ列の近傍に偽ノードを挿入し、**`MutationObserver` 等で削除・差し替えを検知したら再挿入**する。偽ノードは **公式ツイート行の DOM パターンに寄せたマークアップ**とする（詳細は `specification.md` §5）。必要に応じ **`declarativeNetRequest` や `fetch` / `WebSocket` の選択的抑制**を追加フェーズで検討する。
- 拡張 ON 時に「X の更新を全面的に切断」する案は、**初回表示破損**や**エンドポイント変化**のコストが大きいため、**全面ブロックは必須としない**。

## 8. コンプライアンス・倫理の注意（製品メッセージ）

- 本機能は**ローカル表示の演出**である。スクリーンショット等で第三者を誤認させる用途は利用者の責任範囲となるため、オプション画面等で**演出である旨**を短く明示することを推奨する。
